# Put the physics checker inside the decoder

**Closed 2026-10-08, after the AMBER work; phases 2–4 (OpenFOAM, GRPO, LAMMPS) were not run.** On AMBER atom
masks (`docs/research_notes/masks_bench.md`, Gemma-4-31B, 3 runs × 125 tasks) the checker belongs after the
decoder. A grammar lifts the first try from 46% to 64%. A loop that hands ambmask's verdict and lint's hints back
to the model, with reasoning on, reaches 93% from the free first try and 91% from the grammar one. The same loop
with no feedback reaches 57% and fixes none of the 104 rejected masks. That is a verifier-feedback retry loop, a
standard technique, so the result does not carry a placement study, and the rest of the plan below was dropped. The
recipe is kept as `masks/mask_tool.py`.

**Verdict: yes, with one condition. Idea A (checker-guided SMC decoding of simulation input files) is a good project, and C (crossing it with GRPO) is what makes it a research result instead of an application.** The method in A already exists: Loula et al. built SMC decoding with arbitrary checker "potentials" and tested it on code, SQL and molecules ([arXiv 2504.13139](https://arxiv.org/abs/2504.13139)). What the notes found open is the *placement* question. Every simulation-setup agent they located (Foam-Agent, MetaOpenFOAM, PhyNiKCE, SIGA, the LAMMPS evaluation work) runs its validator **after** generation, as a repair loop or an agent-callable tool, and none puts it inside the decoder ([SIGA, arXiv 2606.09774](https://arxiv.org/abs/2606.09774); [Foam-Agent, arXiv 2505.04997](https://arxiv.org/html/2505.04997)). The researchers also searched twice and found no controlled study that crosses {RL-trained, not} × {constrained, unconstrained decoding} on a small model with a semantic checker. So the condition is this: frame the project as "where should a deterministic physics verifier go (in the weights, in the decoder, or after the decoder) and at what compute cost?" If the headline is "GenLM applied to OpenFOAM," it is incremental. Idea B (units-checked decoding) is split. For equations it is already done without an LLM by PhySO ([arXiv 2303.03192](https://arxiv.org/pdf/2303.03192)); for LLM-written Python using pint or astropy the researchers searched and found nothing, but the engineering is hard enough that it fits as a stretch arm, not the core. Recommended shape: OpenFOAM dictionaries as the primary testbed and LAMMPS as the second. AMBER mdin with the existing `md-param-check` serves only as a one-week pilot, because its checker already exists. Models: 0.5–1.5B Qwen for RL and up to 8B for decoding. Stack: genlm-control for SMC, XGrammar/llguidance for the grammar arm, TRL or Unsloth for GRPO. All of it fits a laptop plus about 32 H100-hours if the RL runs are scoped deliberately.

Labeling convention: a claim with a link is sourced from the research notes, which read the source's abstract, README or HTML unless flagged. A claim marked *(inferred)* is my reasoning or the researchers' reasoning and has not been measured. One researcher warned that a WebFetch summary of a PDF (arXiv 2605.02363) invented GRPO arms and 8B models the paper does not have. Treat any detail that came only from a PDF summary or a search snippet as a lead until checked (see the last table).

## Syntax is solved; the headroom is in cross-field physics

Grammar-constrained decoding is commodity infrastructure in 2026. llguidance computes a token mask in **under 50 µs per token for a 128k tokenizer** and ships inside vLLM, SGLang, llama.cpp and OpenAI Structured Outputs ([llguidance README](https://github.com/guidance-ai/llguidance)). XGrammar-2 claims "near-zero end-to-end overhead" in serving systems ([arXiv 2601.04426](https://arxiv.org/abs/2601.04426); search snippet). These engines stop at regular and context-free languages. A constraint like "if `ntc=2` then `ntf=2` and `dt ≤ 0.002`," or "`deltaT` × velocity / cell size ≤ max Courant number," cannot be expressed in any of them *(inferred from the constraint classes the engines list)*. The domain checker has to sit outside the grammar engine: as a custom logits processor, as an SMC potential, or as a post-hoc filter.

The simulation-agent literature shows where the errors actually are. In the LAMMPS study, the parser pass rate rose from **74% to 91%** over a year, yet **only 1 of 80 scripts** on the hardest prompt was fully correct ([Holbrook et al., arXiv 2603.20630](https://arxiv.org/abs/2603.20630)). In multiphysics code generation, **95.5% of generated simulations deployed but only 25.2% satisfied the user's intent** ([arXiv 2605.09360](https://arxiv.org/html/2605.09360)). MDArena's best configuration passed **24 of 50** tasks strictly, and agents "fail on the fine-grained details" ([arXiv 2608.02642](https://arxiv.org/abs/2608.02642)). Together these say the failures are semantic and cross-field, which is exactly the constraint class grammar engines cannot express. That is the case for a physics potential.

The same literature also marks the bar to beat. Foam-Agent's repair loop reaches **83.6% executable success with Claude 3.5 Sonnet, against 55.5% for MetaOpenFOAM**, and removing error correction costs a **55.4% relative drop** ([arXiv 2505.04997](https://arxiv.org/html/2505.04997)). Repair works. Any decode-time claim has to beat a repair loop given the same token budget, not an unconstrained baseline.

Two neighbors deserve a closer look before committing. PhyNiKCE is the nearest thing to A on the physics-rules side: it treats OpenFOAM setup as a constraint-satisfaction problem and reports **96% relative improvement over SOTA baselines and 59% fewer self-correction loops** ([arXiv 2602.11666](https://arxiv.org/html/2602.11666)). The researchers read only its abstract, which describes validating parameters after the LLM proposes them. They did not confirm that it never touches logits. SIGA (June 2026) already built validators for OpenFOAM and LAMMPS, which is useful because they can be reused as checker rules, and a warning because the area is moving fast. Scooping is a real risk on a timescale of months *(inferred)*.

C is the strongest part intellectually because the literature supplies a sharp, testable prediction. Yue et al. find that RLVR models beat their base model at small k, but the base model reaches higher pass@k at large k, and the RL model's reasoning paths "are already included in the base models' sampling distribution" ([arXiv 2504.13837](https://arxiv.org/abs/2504.13837); the claim is contested by [2606.22317](https://arxiv.org/pdf/2606.22317), title only). If that holds, GRPO and SMC approximate the same target, the base distribution conditioned on "checker passes." RL pays for it once in the weights and SMC pays for it on every query. The predictions follow *(inferred)*: RL wins on cost per valid sample at k=1; SMC on the base model catches up at large N and wins on diversity; constrained decoding after RL adds little on constraints RL has learned but still protects the tail and held-out constraint types. Each prediction can come out wrong, and that is what makes it a research question rather than a demo.

## The recommended design is a placement study with three axes

**Testbeds.** The notes support OpenFOAM as the primary testbed. It has the richest task sets: FoamBench with a Basic split and 16 expert-authored Advanced cases ([arXiv 2509.20374](https://arxiv.org/pdf/2509.20374)), NL2FOAM's 28,716 NL-to-config pairs ([AutoCFD repo](https://github.com/YYgroup/AutoCFD), search snippet), and published repair baselines to compare against. LAMMPS is second, with a published parser and normalization pipeline ([2603.20630](https://arxiv.org/abs/2603.20630)) and a tutorial set ([2503.14020](https://arxiv.org/html/2503.14020v1)). The notes found **no public AMBER mdin corpus** and no cross-field AMBER validator, so `md-param-check` is itself a new artifact. AMBER's Fortran-namelist syntax is the easiest grammar of the three, which is why it makes a good one-week pilot and a poor headline. A full OpenFOAM case is several interlinked files, which makes it too long for SMC at 1–8B. I recommend decoding single dictionaries (`controlDict`, `fvSchemes`, `fvSolution`) and conditioning each on the mesh and case description, so that cross-file rules such as the Courant bound become cross-field rules within one decode *(inferred; the specific rule set has to be written and checked against OpenFOAM documentation)*.

**The checker is the central artifact, and its granularity is an experimental axis.** Loula et al. split potentials into cheap incremental ones (Φ_eff, a grammar) and expensive semantic ones (Φ_exp) that are "evaluated post-generation or at meaningful boundaries," at roughly **30 ms per token** when run naively ([arXiv 2504.13139](https://arxiv.org/html/2504.13139)). A key-value config fits the boundary pattern well *(inferred)*. At each completed `key value;` line, a rule is checked only once all the fields it references have been emitted, and rules with a missing side are deferred. That checker is sound at field boundaries (it never rejects a prefix that could still be completed validly) provided that no later token can undo a violation. Soundness breaks in one known way. In a Fortran namelist, a duplicate key overrides the earlier one, so a model can emit `dt=0.004` and "fix" it later. The grammar must forbid duplicate keys, or the prefix checker is unsound *(inferred)*. The notes give the three checker modes that become the experiment's third axis. **Complete-only**: `prefix()` returns neutral, and SMC reduces to importance sampling or rerank. That setting still raised goal inference from **0.063 to 0.289** in Loula et al. **Boundary**: check at line or field ends. **Token-level sound prefix**: usable as a hard mask inside AWRS. For the units stretch arm (B), a units DSL admits a true token-level prefix checker the way PhySO's prior does, which gives the study one testbed at each granularity *(inferred)*.

**Gold is independent of the checker.** For OpenFOAM and LAMMPS, gold is a short, reduced-cost execution: does the case run for N steps without divergence, and do its outputs match the task? That is the same design the LAMMPS study uses ([2603.20630](https://arxiv.org/abs/2603.20630)). Checker-pass minus gold-pass is the reward-hacking metric ([2604.15149](https://arxiv.org/abs/2604.15149) proposes this kind of held-out check). Execution never appears in the RL reward loop, because a checker that takes seconds per sample would dominate GRPO cost at G=8 generations per prompt *(inferred from the notes' cost analysis)*.

**Experimental matrix.** The core is training arm × inference arm, run separately for each checker granularity.

| | Free sampling | Grammar-only mask (XGrammar/llguidance) | Best-of-N + checker | Generate → verify → repair (k rounds, checker message fed back) | SMC: grammar Φ_eff + physics Φ_exp |
|---|---|---|---|---|---|
| **Base model** | baseline | tests the claim "syntax is solved" | unbiased, costs ~1/p_valid per sample | the field's default | the proposed method |
| **RFT** (SFT on checker-passing samples) | cheap training control | | | | |
| **GRPO-LoRA** (checker reward) | "did RL internalize it?" | | | | **the crossed cell** |

RFT is included for a specific reason: it separates "RL" from "saw more valid data" *(inferred; the researchers' proposed STaR-style control)*. A frontier API model running the repair loop on a subset gives the "what the field ships" reference point. Hold constraint types or parameter ranges out of RL training to test generalization, since decode-time enforcement covers anything the checker can express and RL has to generalize to reach them *(inferred)*. Hold prompts fixed and allow reason-then-format: "The Format Tax" finds that format *instructions* cause most of the accuracy loss before any mask is applied ([arXiv 2604.03616](https://arxiv.org/abs/2604.03616)).

**Metrics**, following the literature's standard grid. The first group is validity rate, gold pass (execution), and joint output accuracy (the metric from [2605.02363](https://arxiv.org/abs/2605.02363), abstract-verified only). Then the checker–gold hacking gap and pass@k curves ([Yue et al.](https://arxiv.org/abs/2504.13837)). Then distinct valid outputs per prompt, to catch mode collapse from RL or masking. Then cost as tokens, forward passes, checker calls and wall-clock per valid-and-correct sample, the CARS unit ([OpenReview](https://openreview.net/forum?id=OhndOnT4Ih)). On small enumerable subproblems, add KL to an exact sampler, since CARS samples exactly from the constrained distribution. Report a yield-versus-compute curve for every arm, not a single operating point, plus **the break-even query count** where GRPO's one-time cost equals SMC's accumulated per-query overhead *(inferred design; no paper reports this number)*.

**Models and stack.** genlm-control is the maintained SMC library. A checker becomes a `Potential` subclass with async `prefix()`/`complete()`, is lifted to tokens with `.coerce()`, and runs inside `AWRS(llm, potential)` or as the `critic` in `.smc(n_particles=..., ess_threshold=0.5, critic=...)` ([genlm-control docs](https://genlm.org/genlm-control/getting_started/)). genlm-backend supports **vLLM, SGLang, HF Transformers and MLX-LM "for inference on Apple silicon"** ([genlm-backend](https://github.com/genlm/genlm-backend)), so one codebase runs on the laptop and on PACE. AWRS matters for a Python checker because it tests one candidate token at a time instead of the whole 100k+ vocabulary, which needs "orders of magnitude fewer constraint evaluations" ([arXiv 2504.05410](https://arxiv.org/abs/2504.05410)). The grammar-only arm uses vLLM structured outputs with XGrammar or llguidance. For GRPO, TRL `GRPOTrainer` with `vllm_mode="colocate"` has the best documentation for a single GPU ([TRL docs](https://huggingface.co/docs/trl/grpo_trainer)). Unsloth runs 1.5B GRPO with LoRA in **about 5–7 GB VRAM** ([Unsloth](https://unsloth.ai/blog/r1-reasoning)). mlx-lm-lora supports GRPO on the laptop for debugging the reward ([repo](https://github.com/Goekdeniz-Guelmez/mlx-lm-lora)). Model sizes: 0.5–1.5B Qwen2.5/Qwen3 for everything that trains. For decode-only arms, Llama-3.2-1B-Instruct (the genlm-control README example) up to 8B (Loula et al. used Llama 3.1 8B on an A100).

## About 32 GPU-hours fits, if the RL is sized to one-fifth of ThinkJSON

Decode-time arms at 0.5–1.5B run on the laptop, and the 8B sweeps are short batched vLLM jobs on PACE. PACE ICE has **20 nodes of 8×H100 and 18 of 8×H200** ([PACE ICE](https://pace.gatech.edu/ice-cluster)). The 32 GPU-hour concurrent cap comes from your brief, and the researchers could not verify it because the KB page did not render. Training is the binding cost. ThinkJSON's 1.5B GRPO took **about 20 h on 8×H100, roughly 160 GPU-hours** ([arXiv 2502.14905](https://arxiv.org/abs/2502.14905)), and TRL's 0.5B DeepMath example takes about a day on 8 GPUs ([TRL](https://huggingface.co/docs/trl/grpo_trainer)). A student version therefore needs 0.5B (up to 1.5B) with LoRA, G=8, completions of 512 tokens or fewer (mdin and single dictionaries are short), a millisecond-scale checker, and **runs of 8 h or less so that 3 seeds × 2 training arms fit** *(inferred from the notes' budget arithmetic)*. The notes found no sourced steps-per-hour figure for 1.5B LoRA GRPO on one H100, so a 30-minute pilot that measures throughput comes before any schedule. The API budget covers only the frontier repair-loop reference on a subset of tasks and, optionally, drafting NL task descriptions. The notes give no per-token prices, so estimate after the pilot fixes the token counts.

## Risks: the checker is both the contribution and the attack surface

| Risk | Why it is real | Mitigation |
|---|---|---|
| **Incremental novelty** ("GenLM on a new DSL") | The researchers rated A's novelty risk moderate for exactly this reason; the method is Loula et al.'s ([2504.13139](https://arxiv.org/abs/2504.13139)). | Make the headline placement × granularity × training, not the domain. At least two physics testbeds show the result is not tied to one DSL. |
| **Reward hacking** | RLVR models learn to satisfy verifiers rather than tasks, for example by enumerating labels, and the effect grows with task complexity ([arXiv 2604.15149](https://arxiv.org/abs/2604.15149)). In this domain the likely exploits are omitting a field so that a conditional rule never fires, duplicate keys, and trivially short "safe" configs *(inferred)*. | Execution-based gold evaluator kept out of the reward; report the hacking gap; isomorphic or perturbed task variants; required-field rules; fuzz the checker before RL ([2606.01066](https://arxiv.org/html/2606.01066v1)). |
| **Checker coverage** | Passing the checker is not the same as being correct: 91% parse-valid versus 1/80 fully correct in LAMMPS ([2603.20630](https://arxiv.org/abs/2603.20630)); 95.5% deployable versus 25.2% intent-correct in multiphysics ([2605.09360](https://arxiv.org/html/2605.09360)). | Report validity and gold correctness as separate columns, and never merge them. State the checker's rule list as the claim's scope. |
| **Validity–quality tradeoff** | For molecules, constrained decoding raised validity but "significantly lowers other metrics" ([arXiv 2509.23099](https://arxiv.org/pdf/2509.23099)); greedy masking distorts the distribution ([GAD, 2405.21047](https://arxiv.org/abs/2405.21047)). | This is part of what the study measures: diversity and gold columns, and a KL estimate on small enumerable cases. |
| **Constraint does not bind** | If base models already pass the checker, SMC has nothing to fix. The benefit scales with how often the base model violates the constraint ([AWRS](https://arxiv.org/abs/2504.05410)). | Phase-1 kill criterion; small models; harder tasks with conflicting requirements. |
| **Laptop throughput** | No benchmark of genlm-control on MLX versus vLLM was found; MLX particle batching is probably weaker *(inferred)*. | Develop on MLX, measure on PACE vLLM. |
| **Scooping** | SIGA (June 2026) and the GenLM group are adjacent and active. | Ship the phase-1 table and a short preprint or blog early; the 2×2 is the defensible core. |

## Conclusion

The more interesting fact the notes turned up is that the simulation-agent community and the constrained-decoding community have not met. One has made repair loops very good and never tried putting the checker in the sampler. The other has made checker-in-the-sampler principled (SMC, AWRS, CARS) and tested it on SQL and molecules, never on inputs governed by physical rules. The project's value sits at that seam, and its most defensible output is a number neither side has: the query count at which a GRPO-trained model repays its training cost against SMC on the untrained model, measured separately for each checker granularity.

Your existing asset matters more than it looks. The hard, domain-specific part of this project is a sound, fuzzed, cross-field physics checker with a clean prefix semantics, and you have already built one. Treat MD as the place where that checker came from, generalize it to OpenFOAM and LAMMPS, and put the LLM question in the headline.
